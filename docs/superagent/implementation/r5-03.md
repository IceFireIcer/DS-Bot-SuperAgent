## 交付行为

Main 的 `delegate_work` 接受一至四个独立工作项。每个 WorkBrief 只保留一条原始 Main 消息、一个稳定 `sourceEventId` 和不可变的目标意图列表；多个分项不会复制成多条用户消息。重复提交同一 Main command 返回已有多项回执，同一 command ID 的异文仍拒绝。

Router 通过 `establish_work_plan` 决定一至四项工作。Engine 把规范化分解决定、item ID、原始来源和逐项回执作为一个持久决定保存；identity 由随机生成的持久 item ID 分配，不依赖模型文本顺序或相似度匹配。相同 item 集合即使重新排序也复用原决定；不同目标不会覆盖成功项，而会留下可查询的冲突记录及本次 rejected suggestion，用户必须用新的 Main 请求作出新决定。

每项拥有独立的 Trigger、Decision、Mandate、Ticket、输入订阅、Outbox 与 Worker Assignment。各 Trigger 的 `eventId` 指向同一原始来源，但执行文本、Mandate scope、验收和结果各自独立；现有两个普通 Worker slot 可同时启动，一项变慢或等待不会阻止另一项完成。任何一项的 Decision/Mandate/Session 都不能被另一项复用。

计划与 Ticket 映射采用两个稳定索引：`work-item-ticket` 按 item 查缺项，`work-ticket` 按 Ticket 恢复 Router 回报。Ticket 创建与索引在同一事务提交；如果后续提交暂不可用，已提交项保留、缺项保持 routing，Effect 对账只补齐缺项。Router 重复给出同构计划或进程在部分提交后重启，都不会重建已成功项。

主对话继续复用现有工作卡。同一 WorkBrief 的多个分项分别显示目标、回执、Ticket、状态、验证证据和 artifact；展示顺序来自分解决定中持久化的 position。刷新、重连和重启后 item/Ticket/Report 身份保持稳定，Router 仍只向 Main 发送有界逐项变化。

## 验证

- SQLite 公开 Engine 场景：一条复合请求产生两个 item 与两个 Ticket；两者共享一个来源身份、拥有不同 Decision/Mandate/Ticket/Worker Session，并可并行完成。慢 Worker 运行时另一项已成功，证明局部等待没有串行阻塞。
- 部分提交与重启：第二条 Ticket 首次存储提交故障后，计划和第一条映射保留；新 Engine 对账后只创建缺项，第一条 item/Ticket/Report 身份不变。
- 冲突回归：重启对账时 Router 提出不同第二项。Engine 保留原分项并补齐缺项，同时持久保存本次 `attemptedItems`；原成功项不重派，不同 target 不会借相同 WorkBrief 覆盖成功结果。
- 回执竞态：Ticket/映射已提交但 accepted item 回执首次写入故障时，Worker 仍可完成；结果刷新自动补齐同一 Ticket 的 accepted 回执，随后 Main 成功通知通过当前 Report/Assignment/Ticket 校验。
- 旧 WorkBrief：删除 R5-02 routing brief 的 `sourceEventId` 后恢复，Engine 在分解决定事务中补回唯一来源；单项 Router 决定仍建立并完成真实 Worker。
- 全量回归：Super-agent 557 项中 555 通过、2 项按平台跳过、0 失败（含 PostgreSQL 合约）；DS Bot 1444 项中 1442 通过、2 项按平台跳过、0 失败。类型检查、两组 lint 与 `client.js` 生成一致性通过。

## 边界

本票只完成一条请求内的可靠分项、并行执行、部分恢复与分别回报。自然语言跟进归属、越界 handback、显式停止/恢复、全量工作历史侧栏和真实跨受众发布分别由后续 R5-04、R5-06、R5-05、R5-13 等票完成。

当前产品没有向某 Ticket 授予“发布”能力的入口，因此本票通过独立 Decision/Mandate/Ticket/Session 和同来源派生 Trigger 防止身份/权限借用，但没有执行真实发布权限授予或跨渠道外发的验收。真实模型、真实 GitHub/飞书发布和第二设备组合不在本票证据内。
